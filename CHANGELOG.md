The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased] — Documentation

### Changed

- **Deployment READMEs — parameter/variable enumeration expanded to full coverage:** `deploy/cloudformation/README.md` and `deploy/terraform/README.md` were expanded so their **Parameters** sections enumerate every parameter declared in `CFT-AmazonConnectOperationsReview.yml` and every input variable declared in `deploy/terraform/variables.tf` (plus any additional variables surfaced by the root module via `main.tf` / `parallel.tf`), with — for each entry — name, type, allowed values (where constrained), default value, and a plain-language description of the behavior the default produces. No parameter or variable is omitted from its respective README.

- **Deployment READMEs — new "Differences from the other deployment method" subsections:** Both deployment READMEs now contain a dedicated **Differences from the other deployment method** subsection that explicitly lists every semantic divergence between the CloudFormation parameter surface and the Terraform variable surface (name mismatches, defaults that differ, parameters exposed by only one method, feature-parity gaps). Divergences are called out in both files so a reader of either README learns of every mismatch without having to cross-read.

- **Deployment READMEs — new "Prerequisites" sections:** Both deployment READMEs now contain a dedicated **Prerequisites** section listing required AWS services, required IAM permissions to deploy the stack, IAM permissions the stack itself grants/consumes, required Amazon Connect instance configuration, supported/tested regions, and any account-level quotas that must be raised.

- **Deployment READMEs — new "Post-Deployment Verification" sections:** Both deployment READMEs now contain a dedicated **Post-Deployment Verification** section with an ordered checklist for confirming the stack is working end-to-end — where to find stack outputs, how to trigger the first run (if not automatic), and how/where to view the results (HTML report location, JSON location, Glue catalog location).

- **Audience labels added to every in-scope doc:** The eight in-scope documents (`README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `docs/architecture.md`, `docs/developer-guide.md`, `docs/migration-guide.md`, `docs/cleanup-guide.md`, and both deployment READMEs — `deploy/cloudformation/README.md` and `deploy/terraform/README.md`) plus the new shared reference `docs/parameter-dependencies.md` now carry an explicit audience label at the top declaring the intended reader (repo developer, or deploying customer/TAM), so content aimed at one audience is linked out to rather than intermixed.

### Added

- **New canonical cross-parameter reference — `docs/parameter-dependencies.md`:** A new shared documentation file was introduced as the single canonical reference for every cross-parameter rule that applies across both deployment methods (Glue ↔ raw JSON retention, HTML-report ↔ raw JSON retention, and every additional "IF parameter A is set to value X THEN parameter B MUST/SHOULD be set to value Y, because ..." rule discovered from the template/module). Both deployment READMEs now contain a short **Parameter Dependencies pointer** subsection with a summary table and a link into `docs/parameter-dependencies.md`, rather than duplicating the full IF/THEN table in each README. This eliminates drift between the CloudFormation and Terraform documentation surfaces for cross-parameter behavior.

- **Package-time inline substitution for `docs/parameter-dependencies.md` into release artifacts:** The **Parameter Dependencies** pointer subsections in `deploy/cloudformation/README.md` and `deploy/terraform/README.md` are wrapped in `<!-- BEGIN:parameter-dependencies -->` / `<!-- END:parameter-dependencies -->` marker comments. The `package:cloudformation` and `package:terraform` jobs in `.gitlab-ci.yml` now inline the body of `docs/parameter-dependencies.md` between those markers at package time, followed by a `sed` step that rewrites any cross-file anchor links (originally pointing into `docs/parameter-dependencies.md#...`) into intra-README links so the inlined content resolves within the packaged README. Each release artifact (`cft-release.zip`, `tf-module.tar.gz`) is therefore self-contained with respect to Parameter Dependencies — the customer can follow every dependency reference without needing access to the full repository — and the `docs/` directory does not have to be shipped inside the artifacts.

### Fixed

- **Stale SSM parameter warning in `docs/cleanup-guide.md`:** The cleanup guide previously warned readers that the `ConnectOpsReviewConfig` SSM parameter was retained on teardown (a rc.4 concern documented under Finding #4). That behavior was corrected in v2.0.1-rc.4 — `DeletionPolicy: Retain` / `UpdateReplacePolicy: Retain` were removed from the CloudFormation resource and `prevent_destroy = true` was removed from the Terraform lifecycle block — so the warning had become inaccurate. The guide now reflects that the SSM parameter is deleted with the stack and describes the current teardown behavior.

### Not Changed

- **No CloudFormation template, Terraform module, Lambda source, or non-packaging script was modified.** `.gitlab-ci.yml` was edited only inside the `package:cloudformation` and `package:terraform` jobs to add the package-time inline substitution step described above; no other CI job (lint, test, security scan, publish, etc.) was touched. All historical CHANGELOG entries (rc.4, rc.5, rc.6, and earlier) are byte-preserved.

## [v2.0.1-rc.8] - Unreleased

### Breaking Changes

- **Terraform inline-policy rename for CloudFormation parity (TF-QB-29):** In `deploy/terraform/parallel.tf`, `aws_iam_role_policy.shared_lambda_s3_write.name` has been renamed from `"S3WriteResults"` to `"S3WriteAnalyzerResults"` so the Terraform inline policy name matches the CloudFormation template's `S3WriteAnalyzerResults` inline policy on `SharedLambdaRole`. The `name` attribute on an `aws_iam_role_policy` resource is used to build the inline policy's identifier on the IAM role, so changing it forces Terraform to destroy the existing `S3WriteResults` inline policy and create a new `S3WriteAnalyzerResults` inline policy in its place on `terraform apply` — the shared Lambda role is unchanged, only its inline policy is replaced. This completes the IAM naming-parity work started in QB-49 (rc.6), which aligned the four IAM role *names* between CFN and Terraform but did not touch inline policy names on those roles.

### Migration Guidance

- Run `terraform plan` before applying — the plan will show a destroy + create cycle for `aws_iam_role_policy.shared_lambda_s3_write`. There is a brief window during `terraform apply` in which the shared Lambda role has no S3-write inline policy attached; on a fresh apply this window is invisible (Terraform creates the new policy before any analyzer Lambda is invoked), and it is a non-issue for first-time deploys. If analyzer Lambdas may execute concurrently with the apply, run the apply during a maintenance window. No downstream references to the policy name exist in the module (`aws_iam_role_policy` resources are referenced only by `aws_iam_role.shared_lambda`, which is unchanged), so no other resources are affected.

### References

- See `QUALITY_BACKLOG.md` for full finding details (TF-QB-29). This entry completes the IAM naming-parity work started in QB-49 (rc.6).

## [v2.0.1-rc.6] - Unreleased

### Fixed

- **Executive Summary AI-check hyperlinks resolved to nowhere (QB-50):** Every AI-analyzer check row in the Executive Summary was built by `_render_ai_findings_block` with `anchor="ai-{check_name}"` and rendered as `<a href="#ai-{check_name}">…</a>`, but `_render_ai_structured_finding` emitted the finding's outer `<div>` with no `id=` attribute — so every `#ai-*` link in the Executive Summary pointed at a DOM node that did not exist. Clicking any AI check name in the Executive Summary did nothing. Compounding the defect, `check_order` in `_render_executive_summary` listed AI checks under pre-parallel names (`"Connect AI Agent Inventory"`, `"Connect AI Guardrails"`, `"Connect AI Domain Encryption"`, `"Connect AI Agent Logging"`, `"Connect AI Prompt Configuration"`) while `_render_ai_findings_block` actually emits check rows named `"AI: <suffix>"` (e.g. `"AI: Agent Inventory"`), so no AI check row matched any `check_order` entry — every AI row silently received `check_idx = 99` and drifted to the bottom of its pillar section. Same defect class as QB-58 (Executive Summary hyperlinks resolving nowhere) but for AI findings rather than the Cost pillar. Display-layer fix in two places: (a) added `id="ai-{check_name}"` to the outer `<div>` in `_render_ai_structured_finding` using the same `check_name` that `_render_ai_findings_block` uses to build the anchor; (b) updated `check_order` in `_render_executive_summary` to list the actual `_render_ai_findings_block`-produced names (`"AI: Guardrails"`, `"AI: Domain Encryption"`, `"AI: Agent Inventory"`, `"AI: Prompt Configuration"`, `"AI: Agent Logging"`). Note: `"AI: Hard Limits"` and `"AI: Knowledge Base Capacity"` are intentionally NOT added because QB-53 removes those checks entirely.

- **AI Agents / AI Prompts / AI Guardrails findings lost per-row tables during monolith→parallel port (QB-51):** In the v2.0.0 monolith and in the still-present-but-dead direct renderers (`_render_ai_guardrails`, `_render_ai_domain_encryption`, and the AI Inventory / AI Prompt Configuration blocks in `_render_opex_section`), the three tabular AI findings were rendered as HTML tables — AI Agents listed each agent with its Type and PUBLISHED/DRAFT Visibility badge, AI Prompts listed each prompt with its Type, Model, and Visibility, and AI Guardrails listed each guardrail with a five-filter-column coverage table (Content Filter, Denied Topics, PII Filter, Word Filter, Contextual Grounding). In v2.0.1 the direct renderers no longer fire (they read finding keys like `ai_agent_inventory`, `ai_prompt_configuration`, `ai_guardrails` that the current AI analyzer never emits — the analyzer instead emits pillar-keyed lists under `_ai_structured_findings`). `_render_ai_structured_finding` picked up the structured findings but rendered each as a single colored `<div>` containing only the summary `detail` sentence; the per-agent, per-prompt, and per-guardrail rows the analyzer collects and hands back in each finding's `data` field (`_raw_agents`, `prompts`, `guardrails`, plus the `agent_associations` cross-reference for guardrails) were silently dropped. Root cause: incomplete migration from four direct renderers to a single structured-findings renderer during the parallel port — the structured renderer was intended to be a per-finding replacement but only preserved the summary-detail path and never implemented the per-row tables. Display-layer fix in `_render_ai_structured_finding`: when the finding's `check_name` matches one of the three tabular check names (`agent_inventory`, `prompt_configuration`, `guardrails`) AND the corresponding per-row list is non-empty, the finding's `data` payload is now rendered as an HTML table using the same columns the dead direct renderers used. Non-tabular check names (`domain_encryption`, `agent_logging`, `assistant_discovery`) keep their summary-only format. Empty `data` field or empty per-row list falls back to summary-only unchanged. As a housekeeping side-effect, the four dead direct renderers and their call sites in `_render_security_section` and `_render_opex_section` were deleted — they were unreachable code that would otherwise mask future analyzer schema drift the same way QB-40 was masked. The AI analyzer itself is not modified.

- **Connect AI Agent Logging finding routed to Operational Excellence instead of Observability (QB-52):** `ai_analyzer.py` appended the `agent_logging` finding to `findings["operational_excellence"]` in every code path (success, `AccessDeniedException`, `ResourceNotFoundException`, generic exception). `_merge_analyzer_documents` in `report_generator.py` then merged it into the operational-excellence pillar; `_render_ai_findings_block(pillar_name="Operational Excellence")` rendered it inside the Operational Excellence section and tagged the Executive Summary row `"area": "Operational Excellence"`. But the Executive Summary's `check_order["Observability"]` explicitly listed `"Connect AI Agent Logging"` — indicating that logging is (correctly) an Observability concern, not an Operational Excellence one. The display-layer intent and the analyzer routing disagreed: the finding ended up in the wrong pillar section AND (compounded by QB-50) sorted to the bottom of Operational Excellence because its actual name (`"AI: Agent Logging"`) didn't match any `check_order` entry there either. Root cause: historical pre-parallel monolith pillar assignment carried over — the check was grouped with other AI operational checks under OpEx by convention and the routing was copied verbatim when the AI analyzer was extracted to a standalone Lambda, without questioning whether logging belongs in observability. Two-layer fix: (a) in `ai_analyzer.py`, added `"observability": []` to the pillar-keyed findings dict initialized in `lambda_handler` and re-routed the `agent_logging` finding to `findings["observability"]` in every Check 5 code path (success, AccessDenied/ResourceNotFound, generic error); (b) in `report_generator.py`, added `"observability": "observability"` to `_merge_analyzer_documents`'s `pillar_mapping` so `_ai_structured_findings` is populated on the observability findings dict, and added a `_render_ai_findings_block(pillar_name="Observability")` call at the end of `_render_observability_section` mirroring the pattern already used in `_render_security_section`, `_render_resilience_section`, and `_render_opex_section`. Every other AI-analyzer finding (`guardrails`, `domain_encryption`, `agent_inventory`, `prompt_configuration`, `assistant_discovery`) continues to route to its current pillar unchanged.

### Removed

- **"AI: Hard Limits" and "AI: Knowledge Base Capacity" checks removed — non-adjustable quota utilization provided no actionable signal (QB-53):** `ai_analyzer.check_q_hard_limits` queried Q-in-Connect for the current assistant count and per-assistant knowledge-base count, computed utilization against three hardcoded non-adjustable AWS quotas (5 assistants per account, 10 knowledge bases per assistant, 5000 articles per knowledge base), and emitted two findings: `hard_limits` (routed to `operational_excellence`, rendered as "AI: Hard Limits") and — when knowledge bases exist — `knowledge_base_capacity` (routed to `resilience`, rendered as "AI: Knowledge Base Capacity"). For every Connect instance tested to date, utilization was single-digit percent (1 assistant out of 5, 1–2 KBs out of 10, dozens of articles out of 5000), so both findings consistently rendered `status="pass"` with detail sentences like "Service quota utilization - Assistants: 1/5 (20%); Knowledge Bases: 1/10 (10%)." Two Executive Summary rows and two rendered blocks of noise per report with no actionable information — the underlying quotas cannot be raised, and typical Connect instances are nowhere near any threshold. Removal: deleted `check_q_hard_limits` from `src/lambda/ai_analyzer.py` in its entirety, deleted the Check 6 block in `lambda_handler` (including its `ClientError` / `TimeBudgetExceeded` / generic exception handlers), reduced the `TOTAL_CHECKS` module-level constant from 6 to 5, and deleted the corresponding unit tests (`TestCheckQHardLimits*` in `src/lambda/tests/test_ai_analyzer.py`). Both findings (`hard_limits` and `knowledge_base_capacity`) go away together because they were emitted from the same function — the Executive Summary no longer includes an "AI: Hard Limits" row in the Operational Excellence pillar or an "AI: Knowledge Base Capacity" row in the Resilience pillar, and the corresponding OpEx and Resilience section blocks are gone. **Preserved:** the Capacity Analysis pillar's "Amazon Connect AI Agents Limits" section (rendered under anchor `ai-q1`, powered by `capacity_analyzer.check_ai_agents_limits` via the Service Quotas API) is a different check covering adjustable quotas and is untouched — that section continues to render as it did in rc.5.

### Breaking Changes

- **CloudFormation and Terraform resource replacement for consistent `ConnectOpsReview-` naming (QB-49):** When the CFN template was deployed with any stack name other than `ConnectOpsReview` (for example, a custom stack name used during testing), the auto-named IAM roles, Step Functions state machine, and state-machine log group inherited the stack name while the hard-coded Lambda function names, shared Lambda log group, and EventBridge scheduler retained the `ConnectOpsReview-` prefix — the same deployment therefore contained a visibly mixed prefix set. rc.6 extends the explicit-name convention to the remaining resources: `RoleName: !Sub ConnectOpsReview-<Purpose>Role-${AWS::Region}` on the four IAM roles (`SharedLambdaRole`, `LayerBuilderRole`, `StateMachineExecutionRole`, `SchedulerSFNRole`), `StateMachineName: ConnectOpsReview-Orchestrator` on the state machine, and `LogGroupName: /aws/states/ConnectOpsReview-Orchestrator` on the state-machine log group in the CFN template. In Terraform, `aws_iam_role.shared_lambda`, `aws_iam_role.state_machine_exec`, `aws_iam_role.scheduler_sfn`, `aws_sfn_state_machine.orchestrator`, and `aws_cloudwatch_log_group.state_machine` switch from `name_prefix` to `name` using the same fixed prefixes (region-suffixed via `data.aws_region.current.name` on the account-global IAM roles). IAM role names are account-global (unlike ARNs, which are region-scoped), so the region suffix prevents cross-region same-account collisions when the same stack is instantiated in multiple regions. This forces resource replacement (destroy + create) on any rc.5 → rc.6 stack update for these six resources on CloudFormation (four IAM roles including `LayerBuilderRole` on CFN only, one state machine, one state-machine log group) and five resources on Terraform (three IAM roles, one state machine, one state-machine log group — Terraform does not have a separate layer-builder role). Existing Lambda function names, the shared Lambda log group (`/aws/lambda/ConnectOpsReview-shared`), the EventBridge scheduler (`ConnectOpsReview-RecurringSchedule`), the SSM parameter, the Glue database and its eight Glue tables, and the S3 bucket are preserved unchanged.

### Migration Guidance

Run `terraform plan` (Terraform) or `cloudformation deploy --no-execute-changeset` (CloudFormation) before applying — the plan / changeset will show a destroy + create cycle for the IAM roles, the state machine, and the state-machine log group listed above. All Lambda function role references use the Terraform resource ID (`aws_iam_role.shared_lambda.arn` etc.) or the CFN `!GetAtt <Role>.Arn` intrinsic, so they will automatically track the new ARNs at apply time. The analyzer function `FunctionName` values are unchanged, so every downstream reference to `arn:aws:lambda:<region>:<account>:function:ConnectOpsReview-<Analyzer>` — including EventBridge scheduler targets, state-machine task ARNs baked into execution history, and any external tooling that discovers the analyzers by name — remains valid across the upgrade. Lambda functions will briefly lose their execution role during the replacement window; apply during a maintenance window if concurrent invocations are a concern. No manual intervention is required beyond reviewing the plan / changeset output.

### Notes

- The three display-layer fixes (QB-50, QB-51, QB-52) touch `src/lambda/report_generator.py` and `src/lambda/ai_analyzer.py`. The CFN template's embedded copies are re-synced via `deploy/cloudformation/scripts/update_cft_lambda.py` and Terraform picks up the changes automatically at plan time via `archive_file`.
- The QB-53 removal reduces `ai_analyzer.TOTAL_CHECKS` from 6 to 5. Existing dashboards or external consumers that hardcoded the check count against the AI analyzer will need to be updated; nothing in the analyzer's schema or output keys changes for the remaining five checks.

## [v2.0.1-rc.5] - 2026-08-03

### Fixed

- **Kinesis Data Streams check row on empty-streams branch (QB-47, completes QB-40 rewrite):** During v2.0.1-rc.5 live-testing (a Connect instance with 0 Kinesis streams) the QB-40 Kinesis renderer surfaced no Executive Summary check row despite the observability analyzer emitting a legitimate `status="info"` / `detail="No Kinesis Data Streams associated with this Connect instance"`. Root cause: the QB-40 rewrite placed `checks.append(...)` inside the `if streams_found:` guard, so the row was silently dropped for the empty branch — the exact silent-drop pattern QB-40 was created to eliminate. Unindented the block to sit under the outer `if kds_data:` guard, mirroring the log_groups QB-42 fix pattern. Check row now surfaces for all four analyzer branches (error, empty, warn, pass); the visual `<div id="obs-kinesis-streams">` table remains guarded on `streams_found` being non-empty because rendering a zero-row table adds no signal. Re-verified live: check row now appears with `status=info` and analyzer-provided detail.

- **Kinesis Data Streams alarm-coverage rendering (QB-40, re-fixes rc.4 Finding #9):** The rc.4 attempt at Finding #9 landed non-functional — the Kinesis render block in `report_generator.py` `_render_observability_section()` read keys the observability analyzer never emits (`streams`, `encryption_type`, `retention_hours`, `shard_count`, `total_streams`, `unencrypted_count`), so the `<div id="obs-kinesis-streams">` section and its Executive Summary check row were silently skipped on every run. Rewrote the block to consume the analyzer's actual alarm-coverage payload (`streams_found`, `found`, `missing`, `status`, `detail`), mirroring the CloudWatch Alarm Validation renderer pattern. The section now displays a per-(stream, metric) alarm-coverage table with `MISSING` badges for uncovered alarms and streams status/detail flowing through from the analyzer verbatim.

- **Wisdom-namespace IAM grants for AI analyzer (QB-41, re-fixes rc.4 Finding #8):** The rc.4 attempt at Finding #8 landed non-functional — rc.4 added `arn:aws:wisdom:*:${AWS::AccountId}:*` to the `QConnectReadOnly` policy's Resource list but the Action list still contained only the 14 `qconnect:*` prefixes. AWS's IAM policy evaluation for `GetAssistant` uses the `wisdom:GetAssistant` action name (empirically observed), so `AccessDeniedException` still fired on the AI: Domain Encryption check, producing `Errors=1` in every rc.4 report. Expanded the `QConnectReadOnly` Action list from 14 → 28 entries in both CloudFormation and Terraform by adding a `wisdom:X` counterpart for every existing `qconnect:X` action — belt-and-braces coverage for AWS's qconnect↔wisdom IAM aliasing inconsistency. The existing 14 `qconnect:*` entries and the 2-entry Resource list are preserved verbatim.

- **CloudWatch Log Groups check row dropped when list empty (QB-42):** Same schema-mismatch pattern as QB-40, in the same function. The pre-fix code appended the `CloudWatch Log Retention` check row inside an inner `if log_groups:` guard, so when `check_connect_log_groups` returned an empty list (error branch, or "no Connect log groups found" branch) the check row was silently dropped even though the analyzer had produced a meaningful `status` and `detail`. Flowed analyzer-provided status and detail through verbatim and moved the `checks.append(...)` call outside the inner guard, so the check row now surfaces in the Executive Summary for all four analyzer branches (error, empty, warn, pass). The visual `<div id="obs-log-groups">` table remains guarded on the list being non-empty.

### Notes

- **No breaking changes.** Runtime IAM grants on the shared Lambda role are a strict superset of rc.4 (14 `wisdom:*` actions added, no revocations). No config, parameter, or output schema changes.
- **No migration required.** Existing rc.4 deployments upgrade via a normal stack update — Lambda function code + IAM policy updates only.
- The CFN template's embedded `report_generator.py` copy is byte-identical to `src/lambda/report_generator.py` (re-synced via `deploy/cloudformation/scripts/update_cft_lambda.py`). Terraform picks up the change automatically at plan time via `archive_file`.

- See `QUALITY_BACKLOG.md` for full finding details (QB-40, QB-41, QB-42).

## [v2.0.1-rc.4] - 2026-07-31

### Fixed

- **SSM config parameter retained on teardown blocking redeploy (Finding #4):** Removed `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain` from the CloudFormation `ConnectOpsReviewConfig` resource, and removed `prevent_destroy = true` from the Terraform `aws_ssm_parameter.config` lifecycle block. Fresh redeploys after teardown no longer fail with `ParameterAlreadyExists`.

- **AI analyzer qconnect IAM resource ARN mismatch (Finding #8):** Added dual `qconnect`/`wisdom` ARN namespace to the shared Lambda role IAM policy Resource field in both CloudFormation and Terraform templates. The AI and Resilience analyzers no longer produce `AccessDeniedException` when invoking qconnect API calls.

- **Kinesis Data Streams findings not rendered in HTML report (Finding #9):** Added render block for `kinesis_data_streams` findings in `report_generator.py` `_render_observability_section()`. The Observability section now displays Kinesis Data Streams configuration status when streams are present.

- **Terraform IAM role naming mismatch with CloudFormation convention (Finding #10):** Changed `name_prefix` on `aws_iam_role.shared_lambda` from `"ConnectOpsReview-"` to `"ConnectOpsReview-SharedLambdaRole-"` to align with CloudFormation's naming pattern. Operators can now find the role by searching "SharedLambdaRole" regardless of deployment method.

### Breaking Changes

- **Terraform IAM role replacement (Finding #10 fix):** Existing Terraform deployments will experience an IAM role replacement (`destroy` + `create`) for `aws_iam_role.shared_lambda` due to the `name_prefix` change. Run `terraform plan` to preview — you will see a destroy+create cycle for this resource. All Lambda function role references use the Terraform resource ID (`aws_iam_role.shared_lambda.arn`) and will automatically track the new ARN. No manual intervention is required beyond reviewing the plan output.

### Migration Guidance

1. Run `terraform plan` before applying — confirm the only replacement is `aws_iam_role.shared_lambda`
2. Apply during a maintenance window as Lambda functions will briefly lose their execution role during the replacement
3. Verify Lambda functions resume normal operation after apply completes
